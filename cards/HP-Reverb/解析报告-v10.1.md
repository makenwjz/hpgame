# 哈莉·波特 v10.1 · 角色卡解析报告

> 输入：`哈莉·波特_v10.1.png`（4,434,625 B，SHA256 `4E5913…3D27`）→ `source/card.json`（2,209,167 B，SHA256 `0D1DE1…B6A9`）
> 拆解产物：`_card_parse/hp_v10.1/extract/`（机械生成，未手改）
> 结论全部基于实测；凡未真机跑过的，统一堆在第十节，不混进结论。

## 一、一句话结论

这是一张**把 584 条世界书当数据库、6 个酒馆助手脚本当业务层、2 张 7.5 万字符内嵌 HTML 当前端**的重型 MVU 世界模拟卡。
骨架是 Persona 式的「五维门槛 + 社群 rank 1–10」，肉是 113 个娘化角色 × 4 条人设 + 64 条支线，皮是 1991 年霍格沃茨高等部。

**工程质量比 v10.0 明显干净**（rank 单存储、引导者幽灵容器、CDN 兜底、卡面文案都修了），
但修的全是上一层的表面；这一版真正的硬伤在**提示词层与脚本层的契约断裂**：

> 两个合计 74,592 字符的结算脚本（检定掷骰 36,817 + 好感度结算 37,775），
> 它们等待的 `<roll …/>` 与 `<affinity …/>` 请求格式，**在 584 条世界书里一次都没有被教过**。
> 模型不会写，脚本就永远收不到；而常驻的《正文格式》反过来叫模型直接写 `<check>` 结果——
> 也就是把「骰子握在脚本手里」这条唯一的防作弊设计，从提示词层拆掉了。

同时，卡里宣称的 13 类检定只实现了 6 类；`/能力` 容器在 ZOD 与路径清单里都不存在，但检定脚本照读，
导致**每一次带熟练度的检定都固定吃 −5**；五维修正读的是已被删除的 `/人格` 容器，**恒为 0**。

一句话：**内容资产是 A 级，数值管道是 C 级，两头没接上。**

## 三、世界观设计

### 3.1 三层改动，叠得挺稳

1. **全员娘化 AU**（`娘化 AU 规则` 3,121 字，关键词触发）：113 人一一给出「原名 → 新名」，非人种族按体型分档（妖精＝矮小少女／家养小精灵＝更小一圈／马人＝御姐／狼人＝兽耳娘／人鱼／媚娃／混血巨人）。改名表本身是全卡最扎实的资产之一。
2. **高等部学制**（`高等部学制` 628 字，常驻）：七个年级，一年级入学 18 岁，七年级 24 岁；因此「师生」被改写成「导师与学徒」，宵禁改成门禁。这一步顺手把 NSFW 的年龄争议处理干净了，不用打补丁。
3. **1991 年学年线 + 14 个主线节点**：14 个节点名在 `路径清单`、`第01–07学年`、`正文格式` 三处逐字一致，这是本卡做得最规整的一处。

### 3.2 三条开局 → 实际只剩两条（P1）

- `description`、`创角页`：只有 **哈莉 / 哈利** 两个选项。
- `开局与哈利性别`（常驻 2,110 字）第 4 行却写「三条开局」：原创 / 女性哈莉 / 男性哈利，并重复了一次「哈莉＝原创角色；哈莉＝女性哈莉·波特」——同一标签指了两件事。
- 结果：文本层还在维护「原创主角」分支，UI 与控制器（`GROUPS.opening.values = ['哈莉','哈利']`）都没有它。

### 3.3 第一幕的边界自相矛盾（P1）

- 同一段里先说「终点是**分院**，不是站台」，再列出四拍（车厢 → 渡湖 → 分院 → 午夜宿舍），
  又说「止于第一夜睡梦之前或之中」。
- `第01学年` 事件01 又写「必须写到第三拍的分院……才算出这一幕」；`first_mes` 却对玩家承诺「一路写到霍格沃茨第一夜的睡梦」。

三种终点定义，模型每次开局都要猜一次。

### 4.2 常驻预算

- 22 条 constant，其中 `[initvar]` 是 `enabled=false`（MVU 标准写法，脚本自查、不进提示词）。
- **常驻实际启用 21 条 / 22,202 字符 ≈ 1.5 万 token 每轮**（含 disabled 的 initvar 共 22 条 / 24,611）。

常驻里最重的四条：`变量规则` 4,038、`正文格式` 3,292、`社群口径` 1,570、`社群事件表` 1,316。合计 10,216 字，占常驻启用量 46%——**规则类条目吃掉近一半预算**，这是本卡可优化空间最大的一处。

### 4.3 无 keys / 关闭 / 重复

- 无 keys 21 条：全部是常驻或关闭条目，属正常。
- 关闭 5 条：`[initvar]`、`哈利·波特的出身`（897）、`平行世界的哈莉`（567）、`名器配表`（5,525）、`服装档案`（11,455）。后两条是 v5.1 并入人设后的底稿，共 16,980 字死重，且与人设条目**同 keys**（`名器/配表`、服装六项），一旦有人手动开启就会双份注入。
- 同名 comment 两条：`名器配表`（id 699 disabled / 724 enabled），靠 id 区分，靠人眼维护，是颗定时雷。
- 113 组人设共用同一套 keys ×4 份，`distinct key-sets = 225`，`dup key-sets = 113`——这是设计（四条同触发），不是 bug。

## 五、变量层

### 5.1 实际只有 10 个顶层容器

`主角 / 世界线 / 时空 / 关系 / 社群 / 事件线索 / 五维 / 物品与金钱 / 守护神 / 主角状态`

ZOD（`01__ZOD.js`，5,563 字）与 `路径清单` 完全一致，字段设计干净：
- 全字段 `coerce → catch(兜底) → transform(归一) → prefault(默认)`，模型写错枚举不会崩，只会被夹回去。
- `z.looseObject` 保留未知字段——**这既是自愈能力，也是脏数据的温床**（见 7.1 的幽灵关系键）。
- `record(…, 128)` 用 `takeRight` 截断，超限先丢最旧的，正确。
- 默认值明确：五维全 3、学年 1、日期 1991-09-01、场景「国王十字车站」。

### 5.2 但路径清单说「15 个顶层容器」

`变量规则` 第 96 行：「只用上面列出的 **15 个**顶层容器名写路径」。
实际列了 10 个，ZOD 也是 10 个。这是 v0.1.1 时代（15 容器）留下的数，没跟着改（P1）。

### 5.3 `/能力` 容器不存在，但检定在读写它

- ZOD 无 `/能力`，`路径清单` 无 `/能力`。
- `03__检定掷骰.js` `skillModifier()` 读 `['能力','咒语掌握', spell]` 与 `['能力', skill]`，
  读不到 → `numberOr(…, 0)` → `(0−50)/10 = −5` → **恒为 −5**。
- `正文格式` 还在教模型输出 `<ability kind="咒语" name="荧光闪烁 0→12">`。

也就是说：**熟练度既没有存储处，又在每次检定里扣 5 点**。13 类检定全部受影响（凡带 `skill` 的）。

### 5.4 好感度与 rank 的存储是修好的

v10.0 的三处写 rank（`/社群`、`/关系/社群等级`、状态栏只读后者）已经合并：
- `社群口径`：「两者都在 /关系 下，不存在第二个等级字段」；
- `路径清单`：`社群等级` 标注为「唯一存储处」；
- `ZOD`：`社群` 只剩 `已解锁事件`；
- 状态栏 roster `gate: /关系/{键}/社群等级`。

✅ 这一条修得干净，值得保留。

### 6.1 检定机制（脚本内实测）

```
1d100 低掷成功：掷值 ≤ 判定线 成功；判定线 +15 内 部分成功；其余失败
判定线 = 难度目标 + 修正，夹 5–95
难度：简单 65 / 普通 50 / 困难 35 / 极难 20（结算倍率 0.6 / 1 / 1.4 / 1.8）
骰面 ≤3 大成功（不记伤势）；≥98 大失败（体力与伤势 ×1.5）
修正：属性 ±5、熟练 ±5、情境 ±15、敌人 −5~−15、五维 ±5
结算只写 /主角 的 体力·魔力·声望·伤势 四字段，单次上限 40/40/15/30
retry=true 自动升一档难度，堵刷
```

机制本身很扎实。问题全在入口（7.1）与修正源（7.2–7.3）。

### 6.2 好感度机制

```
触发档位：对话 1 / 帮助 3 / 送礼 3–5 / 共患难 5 / 检定 5 / 任务 10
阶段夹取：陌生 cap3 / 熟悉 cap5 / 亲近 cap5 / 交心 cap10 / 恋慕 cap10
防刷：同「日期+地点+时段」同人一次；同一天同人最多三次
支线状态机：未开始 → 进行中 → 已完成|失败（终态）
rank = 1 + floor(点数/10)，再按 BOND_GATES / BOND_GATES_HIGH 往下压
```

四步校验（名单内 → 幅度夹取 → 防刷 → 状态只进不退）设计正确。

## 七、缺陷清单

### P0 —— 静默失效，且都能量化

**7.1 两个结算脚本的输入契约在提示词里完全不存在**

- 全 584 条世界书检索 `<roll`、`<affinity`：**0 次**（唯一一处是 `路径清单` 第 26 行的一句「由『好感度结算』按 `<affinity>` 结算」，没有格式）。
- `正文格式`（常驻）只定义了 `<scene> <ability> <check> <event> <inner>` 五个模块，并写：
  > `<check>`：只记录**已掷出、已结算**的检定，没掷就整块不出现。

- 模型拿不到掷骰入口，只能二选一：不写 `<check>`（检定永不发生），或者自己编一个「成功｜……」（直接绕开脚本掷骰）。
- 后果：36,817 + 37,775 = **74,592 字符的业务层实际上不参与运行**；数值只剩模型自己写 `<UpdateVariable>` 的一条路。

这是本卡最严重的一处，也是「请求—受理模型」这套好设计被架空的原因。**重构必须把它接回来。**

**7.2 五维修正读的是已删除的 `/人格`**

```js
function personaMod(statData, axis) {
  const raw = statData?.人格?.[axis];   // ← /人格 在 v7.0 已删，值在 /五维
  const v = Number.isFinite(Number(raw)) ? Number(raw) : 1;
  const mod = Math.floor((v - 1) / PERSONA_STEP);   // v=1 → 0
```

`/人格` 不存在 → `raw = undefined` → `v = 1` → `mod = 0`。
**所有检定的人格修正恒为 0**，而脚本头注释、`AXIS_BY_TYPE`、`正文格式` 都在承诺 ±5。

**7.3 13 类检定只实现了 6 类，另 7 类的两条失败路径都很难看**

`CHECK_TYPES` 只有：咒语命中、魔药成败、决斗、疑点调查、说服、潜行。
`正文格式` §六 与脚本注释都写 **13 档**，多出来的 7 类（照料生灵、占卜推断、古文字解读、幻影显形、变形操作、炼金配比、飞行机动）只在 `OUTCOME_LINES` 里有台词，没有 `attr / skill / settle`。

- 模型写 `type="占卜推断"` → `TYPE_ALIAS` 里没有这个键 → `resolveRequest` 返回 `null` → **原始 `<roll>` 标签留在正文里**（控制台 warn）。
- 模型写 `type="占卜"` → 别名命中 `'占卜推断'` → `CHECK_TYPES['占卜推断']` 为 `undefined` → `modifierBreakdown` 第 323 行 `type.attr` → **TypeError**，整轮结算中断。

同一件事有两种坏法：一种漏标签，一种抛异常。

**7.4 `/能力` 缺失，熟练度恒 −5**（详见 5.3）
每一次带 `skill` 的检定都被无理由扣 5 点；同时 `<ability>` 模块写出来的熟练度无处可存。

**7.5 社群等级有三套互相矛盾的门槛规则**

| 来源 | 规则 |
|---|---|
| `社群口径`（常驻） | 每人「最看重的一维」：rank 3 ≥4、6 ≥6、9 ≥8；rank 10 另需任意三维 ≥6 且点数 100 |
| `好感度结算` `BOND_GATES` | 每人**两维**，mid 门槛（5/4 之类）压 rank 3，HIGH 门槛（7/6 之类）压 rank 6 **和** rank 9；不检查 rank 10 的三维条件 |
| `剧情推进` `<event kind="社群">` | **取五维最大值**，cap = 2 / 5 / 8 / 10；**不看点数，不看是谁** |

例：西弗勒丝在 `社群事件表` 里的「最看重的一维」是**心志**；`BOND_GATES` 却要求 **心志 5 + 智识 4**（智识还是已删除的轴名，靠别名折到学业）。
三条路径都能写 `社群等级`，写进去的数会互相打架——这正是 v10.0「等级对不上」问题的**第二形态**：存储统一了，规则没统一。

**7.6 `<event kind="社群">` 的名字格式，两处常驻条目互相冲突**

- `正文格式` §七：「社群写**人物规范名**，rank 另写在 rank 属性里」→ 脚本按这个实现。
- `社群口径` 第 33 行：「用 `<event kind="社群" name="**{人物名}·rank {n}**" date="…">` 标记」。

若模型按 `社群口径` 写，`剧情推进` 会 `ensureObject(stat['关系'], '德拉科娅·马尔福·rank 3')`，
在 `/关系` 下**新建一个不存在的人**，并给它写社群等级。ZOD 的 `record` 照收，UI 的人物页会多出一个怪名字。这是数据污染，不是显示问题。

### P1 —— 文案与现实脱节 / 规则打架

1. **`社群已建立` 被脚本改成了「门槛达标」**
   `好感度结算` 第 676 行：`setAt(..., '社群已建立', gateOk)`。
   而字段定义（ZOD 第 59 行、`路径清单` 第 28 行）是「是否已建立」。
   于是：一个心志 <5 的玩家和斯内普建立社群后，每次结算都会把 `社群已建立` 改回 `false`。
   UI 目前不用这个字段（roster 用 `社群等级 ≥1`），所以是**潜伏 bug**——谁哪天用它做筛选就会翻车。

2. **`变量规则` 里留着两坨孤儿块**
   第 79–81 行「路线开局四选一（生、死、时、空）…等级 0–5…已解锁」，第 85–88 行「体质 / 魔力上限扣减 / 寿命扣减 / 记忆」
   ——这是已删除的 `/权能` 与 `/代价` 的规则碎片，**没有父键、却仍在常驻里每轮进上下文**，
   并且和「全卡只有一套世界观」「15 个容器」一起，给模型一份互相矛盾的路径地图。

3. **名器写入时机，两份常驻直接对立**
   - `变量规则` 第 69 行 + `路径清单` 第 41 行：名器评级与名器「第一次登场随档案写全」。
   - `外貌与人物描写基准` 第 15 行：「第一次性行为**之后**才写后四项（名器／私处／敏感点／反应），此前必须留空」。
   `initvar` 站在前者（三人开局就写名器）。模型每写一个人都要选一边。

4. **人物名在两套写法之间漂移**
   - `鲁贝拉·海格`（人设 4 条 + PEOPLE 名单 + `娘化 AU 规则`）vs `鲁贝娅·海格`（`开局与哈利性别`、`第01–04学年`，12 处）。
   - `布蕾娅·沙比尼`（人设 + PEOPLE）vs `布蕾娅·沙比耶`（`第01学年` 人物表）。
   关系键用规范名，写错一个字就是**两个人、两条社群**。

5. **`支线｜哈莉·波特` 第 10 行文本损坏**
   > 前置条件：本局主角另有其人——开局为哈莉时她是同届同学，开局为哈利时她是另一个世界来的那一位。开局为哈莉时主角就是她本人，本条不启用，也不要把她写成在场人物。**、哈利开局 15。**

   句子断在「人物。、」上，末尾多出一个「15」。原因是「原创局 / 哈莉局 / 哈利局」三个标签被压成两个，压坏了。

6. **`支线｜西弗勒丝` 的结局自相矛盾**
   - 「好感度阶段」第 59 行：「女性哈莉开局**即此档**」（恋慕 81–100）。
   - 同卡 `社群口径`：「谁都不许开局就 rank 2 以上」，初值 0–9。
   - 结局分支编号从 1 跳到 3，缺 2。

7. **「四段」与「五档」混用**
   `好感度阶段（四段…）` 把「亲近 41–60」与「交心 61–80」并成一段，而 `检定与好感度口径` 与 `社群口径` 都按五档定义边界。不是致命，但意味着**支线条目与状态栏对「当前档位」的理解不同**。

8. **`剧情推进` 写回时只传 `stat_data`**
   第 175 行 `replaceMvuData({ stat_data: stat }, …)`，没有 `display_data`。多数 MVU 版本会把整份数据替换掉——**可能清空显示层**。需真机确认（标未验证）。

9. **`剧情推进` 的 rank 会把「剧情需要」凌驾于「玩家经营」之上**
   cap 只看五维最高值：任一维 ≥8 就允许直接跳到 rank 10 的档位，只要 `<event>` 里写 `rank="10"`。这与「点数 100 + 三维 ≥6」的设计完全脱钩。

### P2 —— 维护性

1. 三个脚本的头注释仍是上一代：`检定掷骰` 写「人格六轴」、`世界书控制器` 写「读 `/权能/路线`」、`好感度结算` 的「与人格与羁绊口径逐字一致」——那本口径文件已经不存在了。
2. `检定掷骰` 里 `TALENT_RULES = {}` 与整条天赋分支、`/天赋` 读取全部保留（v6.0 已删天赋）。死代码约 60 行，无害，但会骗维护者。
3. `好感度结算` 的 `TRIGGERS` 还留着 `权能` 档（cap 10），模型写 `kind="权能"` 仍能拿满额好感。
4. 第 663 行 `const mid = BOND_GATES[item.name];` 在块内**遮蔽了外层的 message id**。当前无影响（块内不用 mid），但这是典型的埋雷式命名。
5. `sticky / cooldown / delay` 409 条为 null —— 若前端把 null 当 0 处理，所有条目会变成「每轮必触发」。目前靠 constant + keys 兜着，属于隐性依赖。
6. `order` 有 9995 / 9996 这类哨兵值，与 `变量规则`（9995）、`变量输出格式`（9996）挤在一起；再加条目容易撞号。
7. `creator` 空、无 ccv3、`avatar` 字段缺失。
8. `名器配表` 同名两条；`服装档案` / 旧 `名器配表` 两条 disabled 但同 keys。
