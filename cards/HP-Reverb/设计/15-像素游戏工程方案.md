# 15 · 像素游戏怎么做（工程方案）

> 用户确认：**不排他**。本文件只回答一件事——**这个像素游戏到底怎么做、做多大、怎么一步步落地**。
> 玩法定义见 `06`（探索）/ `10`（战斗）/ `07`（宫殿）/ `08`（塔罗）；本文件是工程视角。

---

## 0. 先说实话：它有多大

按功能点算，这已经不是一个「小游戏」，是一个**中等规模的独立 HTML5 游戏**：

| 模块 | 量级 | 说明 |
|---|---|---|
| 探索层（地图/移动/碰撞/雾） | 1,200 行 | 瓦片、房间、相机、拾取、交互 |
| 战斗层（回合制/BP/Break/队列） | 1,800 行 | 状态机、伤害、护盾、AI、动画时序 |
| 数据表（职业/技能/敌人/道具/地图） | 2,500 行 | 纯数据 |
| UI（HUD/菜单/背包/编队/存档） | 1,200 行 | DOM 为主 |
| 美术（精灵/瓦片/UI 框） | 二进制数据 ~200KB | 程序化像素数组 |
| 音频（方波合成） | 300 行 | WebAudio |
| 适配层（MVU 读写/事件回传/降级） | 600 行 | **最容易被低估的一块** |
| **合计** | **≈7,600 行 + 200KB 素材** | 单人 4–6 周（每天 2–3 小时） |

**结论**：做得完，但**不能一次做完**。必须切片。

---

## 1. 五条工程决策（先说清楚的取舍）

| 决策 | 选择 | 理由 |
|---|---|---|
| 坐标系 | **16px 瓦片，320×180 逻辑分辨率** | GB/GBA 手感；整数缩放不失真 |
| 渲染 | **单 canvas + 离屏缓存** | 不用引擎，自己画；省依赖、省体积 |
| UI | **DOM 叠加，不进 canvas** | 中文排版、滚动、触摸都在 DOM 里解决 |
| 框架 | **零框架，原生 ES 模块** | 卡片要能塞进 worldbook/regex；引框架会让包体爆炸 |
| 打包 | **单个 HTML 文件（内联 JS/CSS/像素数据）** | 酒馆助手前端只认单文件；最终产物 ≤450KB |
| 美术 | **程序化像素数组 + 调色板换色** | 22 人换色不换形；不做 22 套图 |
| 状态 | **游戏内全量状态存 `/宫殿`，前端只做视图** | 刷新页面不丢进度；断线可恢复 |

**不做**：物理引擎、粒子、着色器、滚动视差、多人同步。

## 2. 三个技术难点（真正会卡住的地方）

### 2.1 与酒馆的通信是异步且可能失败的

前端在 iframe 里，变量在 MVU 里，两边不是同步的。

```
前端读：每 200ms 轮询 /宫殿/状态（轻量，只读版本号）
前端写：所有写操作走队列，一次一条，失败重试 3 次
脚本侧：收到 /宫殿/事件 才结算，前端从不自己算数值
```

**关键设计**：前端**不做任何数值计算**，只发"意图"：

```json
{ "type": "move", "to": [12, 7] }
{ "type": "interact", "target": "C", "at": [12, 7] }
{ "type": "battle_action", "actor": "哈利", "action": "attack", "target": "e1", "bp": 2 }
```

脚本算完写回 `/宫殿/结果`，前端读结果演动画。**这样即使前端刷新，也丢不了状态。**

### 2.2 战斗动画与回合结算的时序

回合制最怕"动画还没演完，数值已经变了"。解法：

```
① 前端发 action → 脚本算 → 返回 {events: [...]}
② 前端按 events 顺序播放动画（每个 event 有 duration）
③ 播放完毕才允许下一回合
④ 若 3 秒内没收到结果 → 显示"结算中"，允许跳过动画直接看数字
```

**events 是纯文本序列**，比如：
`[{t:"dmg",target:"e1",v:37,crit:false},{t:"break",target:"e1"},{t:"log",text:"护盾破开"}]`

### 2.3 中文像素字体

**不做点阵中文字库**（一个 8×8 中文子集也要 20KB+，且缺字）。
方案：canvas 只画图，**所有文字用 DOM**（`position:absolute` 叠在 canvas 上）。
代价：文字不能随相机缩放；接受。

## 3. 代码结构

```
pixel/
├── index.html          # 单文件入口（构建后内联一切）
├── src/
│   ├── main.js         # 引导、场景栈、主循环
│   ├── engine/
│   │   ├── loop.js     # 固定步长 60fps + 插值
│   │   ├── input.js    # 键盘 / 触摸 / 虚拟十字键
│   │   ├── render.js   # 瓦片层、精灵层、雾、调色板
│   │   ├── audio.js    # WebAudio 方波，12 音效 + 4 BGM
│   │   └── rng.js      # 种子随机（与脚本同算法）
│   ├── scenes/
│   │   ├── explore.js  # 探索：地图、移动、碰撞、交互
│   │   ├── battle.js   # 战斗：队列、指令、BP、Break、动画
│   │   ├── menu.js     # 编队 / 背包 / 状态
│   │   └── result.js   # 结算 / 撤离 / 改心
│   ├── data/
│   │   ├── jobs.js     # 8 职业 × 6 技能
│   │   ├── enemies.js  # 24 敌人（含 6 Boss）
│   │   ├── items.js    # 12 消耗品 + 装备
│   │   ├── pals.js     # 9 宫殿的地图模板与瓦片集
│   │   └── palette.js  # 9 套 16 色调色板
│   ├── art/
│   │   ├── sprites.js  # 8 职业 × 4 向 × 3 帧（像素数组字符串）
│   │   ├── tiles.js    # 瓦片集
│   │   └── ui.js       # 9-slice 框
│   └── bridge.js       # MVU 读写、事件回传、降级
└── build.mjs           # 内联打包成单 HTML
```

**行数预算**：engine 900 / scenes 1,600 / data 2,500 / art 800 / bridge 300 / ui 700 ≈ **6,800 行**。

## 4. 美术怎么办（这是最容易被拖垮的部分）

### 4.1 三条硬规矩

1. **不用外部图片**。所有像素以字符串数组内联：
   ```js
   const HERO = ["..1111..", ".122221.", "12233221", /* ... */];
   // 数字 = 调色板索引，. = 透明
   ```
2. **22 人 = 8 套身体 × 22 组配色**。不画 22 个人。
3. **每座宫殿只换 16 色调色板 + 瓦片贴图**，不换结构。

### 4.2 素材清单（实际要画的东西）

| 类别 | 数量 | 尺寸 | 估时 |
|---|---:|---|---:|
| 职业身体（4 向 × 3 帧） | 8 × 12 = 96 帧 | 16×16 | 2 天 |
| 敌人 | 24 种 | 32×32 / 48×48 | 2 天 |
| 瓦片集 | 1 套 48 块（9 宫殿靠换色 + 叠图） | 16×16 | 1.5 天 |
| UI 框（9-slice） | 4 种 | — | 0.5 天 |
| 特效（斩/爆/回复/破防） | 8 种 | 32×32 | 1 天 |
| 图标（道具/状态） | 24 个 | 16×16 | 0.5 天 |
| **合计** | — | — | **7.5 天** |

**如果时间紧**：先用色块占位（每个精灵用一个 16×16 的纯色矩形 + 1px 描边），把系统跑通，最后再替换。**占位图不影响任何逻辑。**

## 5. 分四步做（每步都能玩）

### 第 1 步 · 「能走」——3 天

| 交付 | 验收 |
|---|---|
| 单文件 HTML，320×180 自适应 | 手机竖屏、桌面都居中 |
| 一张 24×18 的手写房间 | 能走、能撞墙、能开一个箱子 |
| 虚拟方向键 + 键盘 | 触屏可玩 |
| 写回 `/宫殿/位置` | 刷新后回到原位 |

**这一步做完，你就有一个能走的像素房间了。** 系统一行都不用写。

### 第 2 步 · 「能打」——5 天

| 交付 | 验收 |
|---|---|
| 随机遇敌 → 进战斗 → 回地图 | 一次完整循环 |
| 回合指令 + BP + 护盾 Break | 打出一次 Break |
| 1 个敌人、1 套技能（剑士） | 3 回合内解决 |
| 结算写回 HP/MP | 战斗后地图上血量变化 |

**此时把它给朋友玩，会得到最真实的反馈**（哪里无聊、哪里看不懂）。

### 第 3 步 · 「能通关」——6 天

| 交付 | 验收 |
|---|---|
| 斯内普宫殿 4 层（程序生成） | 灯火、警戒、安全屋、机关 |
| 3 种敌人 + 1 个 Boss（三阶段） | 打完出秘宝 |
| 碎片 3 块 + 改心判定 | 条件齐 → 提示改心 |
| 撤离 / 全灭 / 打断 | 三条失败路径都能走完 |
| ASCII 降级 | 关掉 canvas 也能玩 |

**这一步做完 = 垂直切片完成**，可以对外说"能玩了"。

### 第 4 步 · 「能铺」——10–15 天

| 交付 | 验收 |
|---|---|
| 9 套调色板 + 9 张地图模板 | 每座宫殿长得不一样 |
| 8 职业 + 24 敌人 + 12 道具 | 数据表齐全 |
| 22 人配色 + 编队 | 换人正常 |
| BGM / 音效 | 可静音 |
| 存档 / 读档 / 跨层续玩 | 断线可恢复 |

## 7. 风险与对策

| 风险 | 概率 | 对策 |
|---|---|---|
| 前端体积超限（worldbook 塞不下） | 中 | 单文件 ≤450KB；素材用像素数组压缩；超了就外链 CDN（最后才用） |
| 酒馆 iframe 沙盒限制 | 中 | 提前用最小 demo 验证 canvas、WebAudio、localStorage |
| 中文 UI 排版崩 | 高 | 全部 DOM，不用 canvas 画字；固定 line-height |
| 战斗节奏太慢拖累聊天 | 高 | 自动战斗 + 跳过动画 + 3 秒超时 |
| 像素美术耗时失控 | 高 | 先占位色块，逻辑优先；美术最后集中做 |
| 与模型叙事脱节 | 中 | 每层只让模型写 1–2 段；模型只拿摘要 |
| 存档与 MVU 冲突 | 中 | 前端只读；写全部经脚本；版本号防覆盖 |

## 8. 我最先做的那个 demo（本周就能给你看）

**最小可玩**（≤800 行）：

```
1 张 24×18 地图 + 主角 + 走 + 撞墙 + 开箱 + 一个敌人 + 一次 Break
```

因为：**只要「走」和「Break」两件事的手感对了，剩下全是堆量。**
如果这两件事不好玩，再多系统也救不回来。

## 9. 一句话

**这个像素游戏不是一个功能，是一个作品。**
做法只有一条：**先做能走的房间，再做能打的战斗，最后才是 9 座宫殿。**
任何打算"先把 22 个人、9 座宫殿、8 个职业写完再动手"的计划，都会在第二个星期停下来。

## 10. 两版合并口径（本会话对齐）

本文件此前由并行会话落盘。以下是**两版并集后的权威结论**，冲突时以此为准：

| 项 | 口径 |
|---|---|
| 体量 | **≈8,000–12,000 行 + 约 200KB 程序化像素数据**；单 HTML ≤450KB |
| 分辨率 | 320×180，16px 瓦片，**走格移动**（不做平滑插值，省三块工作量） |
| 渲染 | 单 canvas + 离屏缓存 + 脏区重绘；**文字全走 DOM** |
| 权威方 | **脚本/数据表是权威，前端只是视图**；前端只发意图，不裁决数值 |
| 通信 | 节流 200ms 读；写走队列、失败重试 3 次；事件请求 `{type,payload}` 单向 |
| 战斗时序 | 前端发 action → 规则层算 → 返回 `events[]` → 按序播动画 → 才允许下一回合；3 秒超时提示「结算中」，可跳过动画只看数字 |
| 美术 | 4–8 套身体 × 22 组配色；每宫殿 16 色 + 一套瓦片集换色；**先占位色块，逻辑优先** |
| 降级 | 永远保留 **ASCII 模式**与「自动探索」（只出摘要） |
| 交付 | 四步：能走（3 天）→ 能打（5 天）→ 能通关（6 天）→ 能铺（10–15 天）；**M1 切片共 14 天** |
| 总工期 | 约 **41 个工作日**，按每天 2–3 小时，**两个月** |
| 最贵的部分 | 那 120 帧手画像素（约 7.5 天），且**不随内容增加而变贵** |

**唯一新增的硬规定**：`battle/rules.js` 必须是纯函数（不碰 DOM、不碰 MVU），这样能在 Node 里跑单测——
v10.1 最大的教训就是「数值逻辑和渲染/存储缠在一起，坏了看不出来」。
