# 16 · 插件分发与版本更新

> 问题：**卡放 GitHub，导入后自动下载插件；插件能按版本号本地更新。**
> 结论先说：**能做到，但"自动"这层必须换词——SillyTavern 没有"导入卡就装扩展"的通用口子。**
> 现实可行的组合是：**卡 = 卡片 + 世界书 + 正则 + 一组加载脚本；代码在 GitHub；脚本带版本号自更新。**
> 本文件给方案、契约、目录结构、更新协议与风险，最后给一段「未验证项」——所有运行时结论都不越界。

---

## 0. 一句话方案

```
GitHub 仓库（一个）
├─ dist/v1.0.0/          ← 不可变发布物（构建产物 + manifest + sha256）
├─ dist/v2.0.0/
├─ dist/latest.json      ← 指针 + 版本 + 哈希 + 最低 ST 版本
└─ .github/workflows/    ← 打 tag 自动构建、算哈希、写 latest.json

卡片里只有：
├─ 世界书 300 条
├─ 正则 5 条
└─ 1 个 loader 脚本（~200 行）——读 latest.json → 比对版本 → 下载 → 注册
```

**装一次卡，以后靠版本号更新。** 不联网时用卡里内置的离线快照兜底。

## 0.5 走酒馆助手的路线（推荐，优先于本文其余部分）

酒馆助手（JS-Slash-Runner）本身就是"加载远程代码"的方案，不用自己发明协议。它提供三层现成能力：

| 能力 | 酒馆助手的做法 | 谁维护 | 我们用不用 |
|---|---|---|---|
| **酒馆助手脚本** | 卡片扩展字段里存脚本；可在「脚本库」里按 Git/GitHub URL **导入并随版本更新** | 酒馆助手 | ✅ **主路径** |
| **前端界面** | 卡内 `xxx/` 目录（`index.ts` + `index.html`），由助手构建并挂 iframe | 酒馆助手 | ✅ 宫殿像素游戏 |
| **变量 / 世界书 / 正则** | `getVariables`、`getWorldbook`、`updateWorldbookWith` 等 | 酒馆助手 | ✅ 已有 |

**主路径改成这样：**

```
GitHub 仓库（一个，按语义化版本打 tag）
├─ src/                 ← 源码（TS/JS）
├─ dist/<版本>/          ← 构建产物（脚本 bundle、前端 bundle、数据 json）
├─ package.json / manifest
└─ .github/workflows/   ← 打 tag 构建 + 三检查

酒馆助手（用户侧）
├─「脚本库 → 从 URL 导入」填我们的仓库地址
│   → 助手负责下载、缓存、版本更新
├─ 卡内脚本只留一个 boot.js（读版本、做兼容检查、报错提示）
└─ 宫殿前端走卡内前端界面目录，助手构建
```

**这么做的四个好处**

1. **不用自己写 loader**：下载、缓存、版本比较是酒馆助手的能力，不是我们的代码。
2. **更新交给工具**：用户在助手里点「更新」，或用它自己的版本机制，不需要我们维护 `latest.json` 那套自造协议。
3. **失败面小**：助手加载失败会在它的界面报错，不用我们猜为什么 `import()` 静默失败。
4. **许可干净**：我们发的是"脚本 + 前端"，不是"扩展"，不触碰 ST 扩展生态的规则。

**代价**：用户必须装酒馆助手（本来就是本卡的硬依赖），且"更新"是**在助手界面里点一下**，不是完全无感的自动更新。

> 下文 §1–§13 保留为**备用路径**（不装助手 / 助手版本过老 / 需要完全离线时）。
> 两条路径共用同一份 `dist/` 产物与同一套版本纪律，不冲突。

## 1. 先破三个幻想

| 幻想 | 现实 |
|---|---|
| "导入角色卡会自动安装扩展" | ❌ 没有这种机制。卡能自带的是**世界书 / 正则 / 酒馆助手脚本**，不是 ST 扩展 |
| "脚本能随意 `import()` 远程模块" | ⚠️ 能 import **ES 模块**，但受 CSP、跨域、CORS、GitHub 的 `Content-Type` 影响；`import()` 失败是静默的，必须自己兜 |
| "更新只要改 main 分支" | ❌ 用 `main` 当版本号等于没有版本。必须 **immutable tag + 哈希**，否则一次误推就把所有人的卡弄坏 |

**v10.1 已经踩过第 3 条的边**：它用 `@v1.0.1` 钉住 CDN，四个镜像兜底——这是对的做法，只是没做自更新。

## 2. 架构：三层职责

| 层 | 放哪 | 职责 | 更新方式 |
|---|---|---|---|
| **卡本体** | `chara` 卡 PNG | 人设、世界书、正则、loader 脚本 | 重导卡（ST 支持"用文件替换"） |
| **逻辑** | GitHub `dist/<ver>/` | 9 个业务脚本、宫殿前端、数据表 | **自动**（loader 拉） |
| **依赖** | CDN / npm 镜像 | MVU 内核、Zod | 跟随逻辑层锁定的版本 |

**分层原则**：卡本体尽量**薄且稳定**（一年动一次），逻辑层可以**频繁更新**（一周动几次）。

## 3. 目录结构

```
hp-reverb/
├─ dist/
│  ├─ latest.json                 ← 唯一可变文件（但只由 CI 写）
│  ├─ 1.0.0/
│  │  ├─ manifest.json            ← 版本、兼容性、文件清单、哈希
│  │  ├─ core.mjs                 ← 核心（日程/社群/检定/剧情）
│  │  ├─ palace.mjs               ← 宫殿 + 战斗
│  │  ├─ ui.mjs                   ← 状态栏渲染
│  │  ├─ data/
│  │  │  ├─ chars.json            ← 121 人（塔罗 22 + 攻略层）
│  │  │  ├─ palaces.json          ← 9 主宫殿 + 13 回响房
│  │  │  ├─ jobs.json             ← 8 职业 + 技能
│  │  │  └─ enemies.json          ← 24 敌人 + Boss
│  │  └─ palace.html              ← 像素游戏单文件（≤450KB）
│  └─ 1.1.0/ …
├─ src/                           ← 源码（构建产物不进 dist 之外）
├─ tools/build.mjs                ← 打包 + 算哈希
├─ tools/check.mjs                ← 契约/路径/人名三检查
└─ .github/workflows/release.yml
```

**为什么把 `data/*.json` 单独拆出来**：改数值不用重发代码，前端和脚本都能读同一份。

## 4. 清单格式（manifest + latest）

### 4.1 `latest.json`（唯一入口，CI 自动写）

```json
{
  "schema": 1,
  "channel": "stable",
  "version": "1.1.0",
  "published_at": "2026-11-02T10:00:00Z",
  "min_card_version": "1.0.0",
  "min_st": "1.12.0",
  "min_helper": "4.8.0",
  "notes": "修宫殿第 3 层灯火；新增韦斯莱家 9 人数据",
  "manifest_url": "https://raw.githubusercontent.com/<org>/hp-reverb/v1.1.0/dist/1.1.0/manifest.json",
  "manifest_sha256": "…",
  "signature": "…"            
}
```

### 4.2 `manifest.json`（版本内，不可变）

```json
{
  "version": "1.1.0",
  "files": [
    { "path": "core.mjs",   "sha256": "…", "bytes": 84213 },
    { "path": "palace.mjs", "sha256": "…", "bytes": 128004 },
    { "path": "ui.mjs",     "sha256": "…", "bytes": 30122 },
    { "path": "data/chars.json", "sha256": "…", "bytes": 61200 }
  ],
  "entry": "core.mjs",
  "compat": { "stat_schema": 3, "contract": "2026-11-a" }
}
```

**四条硬规矩**

1. 发布目录**永不覆盖**：改了就是新版本。
2. `latest.json` 只做指针，**逻辑全在版本目录里**。
3. 每个文件都带 `sha256`，下载后校验。
4. `compat.stat_schema` 与卡内变量 schema 绑定——不兼容就**拒绝加载并提示重导卡**，而不是硬跑。

## 5. 卡内 loader 脚本（约 200 行）

### 5.1 职责

```
① 读卡内常量：CARD_VERSION、REPO、CHANNEL、内置快照版本
② 检查缓存（localStorage）：已装版本 + 哈希
③ 拉 latest.json（带 ETag / If-None-Match 省流量）
④ 版本判定：
   latest > 已装  → 下载
   latest = 已装  → 跳过
   latest < 已装  → 询问是否回退（默认不）
⑤ 下载 manifest + 逐文件，校验 sha256
⑥ 写入缓存（localStorage / IndexedDB）
⑦ 动态 import 入口，注册脚本
⑧ 失败 → 回退内置快照；再失败 → 错误卡
```

### 5.2 版本比较

```
major 不同 → 必须重导卡（提示）
minor 不同 → 自动更新
patch 不同 → 自动更新
prerelease  → 只在 channel = "beta" 时接受
```

### 5.3 更新时机（关键）

**不在对话进行中更新。** 只在三个时机检查：

| 时机 | 行为 |
|---|---|
| `CHAT_CHANGED` | 静默检查，有新版就在状态栏点一个点 |
| 状态栏「设置」页 | 手动「检查更新」按钮 |
| 卡导入后的第一条消息 | 强制检查一次（可关） |

**更新落地**：先用新版本跑一次「自检」，通过才替换；失败保留旧版。

### 5.4 缓存与体积

| 项 | 大小 | 存哪 |
|---|---:|---|
| 已装版本（1 份） | ~350 KB | IndexedDB |
| 上一版（回滚用） | ~350 KB | IndexedDB |
| 内置快照 | ~120 KB | 卡内（压缩后） |

**保留两版**：当前 + 上一版。三版以上收益低，占用高。

## 6. 部署流程（CI）

```yaml
# .github/workflows/release.yml
on:
  push:
    tags: ['v*']
jobs:
  release:
    steps:
      - checkout
      - node tools/build.mjs            # 打包 dist/<ver>/
      - node tools/check.mjs            # 契约/路径/人名三检查，不过就 fail
      - node tools/hash.mjs             # 生成 manifest.json（含 sha256）
      - node tools/latest.mjs           # 更新 latest.json（指针）
      - gh release create …             # 附上 zip 与哈希
      - commit latest.json to main
```

**三道闸门**：构建成功 → 三个一致性检查通过 → 哈希与清单一致。任一失败，`latest.json` 不动。

## 7. 版本号纪律

| 变化 | 升哪一位 | 例子 |
|---|---|---|
| 加人、加宫殿、改数值 | **minor** | 1.1.0 → 1.2.0 |
| 修 bug、改文案 | **patch** | 1.2.0 → 1.2.1 |
| 变量 schema 变了 | **major**（且卡要重导） | 1.2.1 → 2.0.0 |
| 只改卡内世界书 | 卡版本（`character_version`） | 卡 1.0.3 |

**卡版本与插件版本分开记**，状态栏同时显示 `卡 1.0.3 / 插件 1.2.1`。

## 8. 离线与失败降级

| 场景 | 行为 |
|---|---|
| 完全断网 | 用内置快照（功能受限：无像素宫殿、无 121 人全量数据） |
| GitHub 被墙 | 备用镜像（jsDelivr / Statically）拉同一份版本目录 |
| 分支被 force push | 用 **tag + 哈希**，force push 不影响已发布版本 |
| 缓存损坏 | 哈希校验失败 → 丢弃缓存 → 重新下载 → 仍失败用快照 |
| 新版本崩溃 | loader 捕获 → 自动回滚上一版 → 状态栏提示「已回滚，请报告」 |

**镜像顺序**：`raw.githubusercontent` → `jsDelivr` → `Statically` → 内置快照。

## 9. 安全

| 风险 | 对策 |
|---|---|
| 仓库被篡改 | 发布分支保护 + tag 签名（GPG）+ manifest 哈希 |
| 供应链劫持（CDN） | 哈希校验（CDN 只能改内容，改了就对不上） |
| 任意代码执行 | 只加载自己仓库、**固定 org/repo**，不允许用户填 URL |
| 隐私 | loader 只发 `If-None-Match`，不发送聊天内容、不发用户标识 |
| 许可 | 依赖（MVU/Zod/TH）各自的许可证要在 `NOTICE` 里列清 |

**重要**：加载远程代码本身是**用户授权的行为**。卡内要明示「本卡会从 GitHub 下载脚本」，并提供关闭开关（关 = 只用内置快照）。

## 10. 这套方案解决 v10.1 的什么毛病

| v10.1 的问题 | 本方案 |
|---|---|
| 脚本锁死在卡里，改一个字符要重导整卡 | 逻辑与卡分离，改逻辑只发 minor |
| 远程 import 无版本、无哈希、无回退 | manifest + sha256 + 回滚 |
| 四个 CDN 镜像靠人肉维护 | loader 统一镜像链 + 缓存 |
| 用户不知道自己在跑哪个版本 | 状态栏显示 `卡 x.y.z / 插件 a.b.c` |
| 契约与脚本漂移 | CI 三检查，不过不发布 |

## 10.5 酒馆助手路线下的 8 项探针（替代 §11 的前三条）

走助手路线时，需要验证的东西变了——重点从「我们能不能 import()」变成「助手怎么加载、怎么更新」：

| # | 待验证 | 怎么验 | 不成立时的降级 |
|---:|---|---|---|
| 1 | 助手「脚本库」能否按 GitHub URL 导入并识别版本 | 建一个空仓库，放一个 `console.log` 脚本，导入 | 改成本地 zip 导入 |
| 2 | 导入后助手如何更新（自动 / 手动 / 跟随 tag） | 打新 tag，看助手里是否提示 | 手动点更新，写进说明 |
| 3 | 卡内前端界面目录的构建要求（`index.ts` + `index.html`） | 放最小 demo，看是否渲染 | 退回正则 + 内联 HTML |
| 4 | 卡内脚本与「脚本库」脚本的加载顺序与作用域 | 两个脚本互相读一个全局变量 | 显式等待 + `waitGlobalInitialized` |
| 5 | 前端的 iframe 能否读写 MVU | 前端读 `/宫殿/位置` 并写回 | 前端只读，全部经脚本 |
| 6 | 切换聊天时脚本重入是否重复注册 | 切 3 次，数事件绑定 | 加 `dispose` 与幂等保护 |
| 7 | 卡「用文件替换」是否保留脚本 | 导两次对比 | 说明里写「需重新导入脚本」 |
| 8 | 4 个镜像在目标网络下的可用性 | 逐个 HEAD | 提供离线 zip |

> **1 与 2 是决定性的**：它们决定「版本更新」是自动、半自动、还是手动。其余都是工程细节。

## 11. 未验证项（必须真机确认，否则不承诺）

静态设计与公开资料**不能**证明下面这些，M1 之前要用最小 demo 逐个打勾：

| # | 待验证 | 探针 |
|---:|---|---|
| 1 | 卡内脚本能否 `import()` GitHub 的 `.mjs`（MIME / CORS） | 在一个测试卡里 import 一个 3 行模块，看是否 resolve |
| 2 | `raw.githubusercontent.com` 与 jsDelivr 的实际 MIME 与缓存头 | `curl -I` 对比 |
| 3 | 酒馆助手 iframe 内的 CSP 是否允许 `script-src` 远程 | 在前端里试 fetch + dynamic import |
| 4 | IndexedDB 在消息 iframe 里是否可写 | 写读一遍 |
| 5 | 更新后 `import()` 是否绕过模块缓存（需要 `?v=` 或 `import()` 新 URL） | 同 URL 换内容测两次 |
| 6 | `CHAT_CHANGED` 时脚本重入是否重复注册 | 切聊天 3 次看事件绑定数 |
| 7 | 卡片"用文件替换"是否保留脚本（还是整卡覆盖） | 导两次对比 |
| 8 | 4 个镜像在目标网络下的可用性 | 逐个 HEAD 请求 |

> 这 8 条里 **1、3、5 是决定性的**：任一条不成立，"自动下载 + 热更新"就得降级成"手动下载 zip 放进去"。

## 13. 一句话（修订）

**别自己造下载器——酒馆助手就是那个下载器。**
卡负责「说清楚要什么版本」，助手负责「把代码拉下来并缓存」，我们只负责「代码与版本号本身不撒谎」。
自造 loader 只在助手不可用时兜底，不是主路。

## 14. 旧版一句话（备用路径）

**卡不应该装代码，卡应该指向代码。**

**卡不应该装代码，卡应该指向代码。**
把"版本号"当成唯一真理：写死 tag、算哈希、留回滚、不覆盖发布物——
这样你才能既享受"改一处全员生效"，又不会一次手滑把所有人的存档弄坏。
